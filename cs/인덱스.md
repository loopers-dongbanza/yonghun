# 인덱스(Index) · 옵티마이저(Optimizer) · SQL 실행 계획 정리

---

## 1. 인덱스가 뭔데, DB는 이걸 어떻게 아는가?

**인덱스 = 정렬된 자료구조(B-Tree 등)에 Key–Value 형태로 데이터를 저장해서  
검색 범위를 빠르게 줄이는 장치**  
(책 뒤 목차/색인과 동일한 개념)

`CREATE INDEX ...` 를 실행하면:

- 인덱스 정보(타입, 대상 컬럼, 저장 구조 등)가 **시스템 카탈로그(메타데이터 저장소)**에 기록됨.
- DB 엔진·옵티마이저는 이 메타데이터를 보고 **“이건 인덱스 객체야”**라고 인식하고 쿼리 최적화/실행에 활용함.

즉,

- **DB가 직접 인덱스를 기억하는 게 아니라, 시스템 카탈로그가 인덱스를 ‘기억’한다.**
- 옵티마이저는 이 정보를 기반으로 실행 계획을 만든다.

### 인덱스 생성 예시 (RDB 기준)

```sql
-- 단일 컬럼
CREATE INDEX idx_user_name ON users (name);

-- 복합 인덱스
CREATE INDEX idx_user_name_age ON users (name, age);

-- 유니크 인덱스
CREATE UNIQUE INDEX idx_user_email_uniq ON users (email);

-- 정렬 최적화
CREATE INDEX idx_order_created_desc ON orders (created_at DESC);
```
## 2. 옵티마이저가 실제로 하는 일

### 정의
쿼리를 실행할 때 **가장 비용이 적은 실행 계획**을 자동으로 선택하는 엔진.

### 역할 3단계
1. 가능한 실행 방법을 **여러 개 생성**한다.  
2. 각 실행 방법의 **비용(Cost)** 을 계산한다. (통계 정보 기반)  
3. 가장 비용이 낮은 **최적 실행 계획을 선택**한다.

### 브루트포스인가? → 아니다
겉으로 보면 “모든 경우의 수를 탐색하는 브루트포스”처럼 보이지만 실제로는 전체 탐색을 하지 않는다.

- 통계 정보와 휴리스틱을 이용해  
  **비용이 커 보이는 후보는 초기에 제거(pruning)**  
- **동적 계획법(DP)**, **비용 기반 탐색(CBO)** 으로 유망한 후보만 남긴다.

## 3. SQL 문법 vs 실제 실행 순서 (Execution Plan)

### 우리가 쓰는 SQL 문법 순서
SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY

shell
코드 복사

### DB가 실제로 처리하는 논리적 순서
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

markdown
코드 복사

### 이 차이가 중요한 이유
- SQL은 **선언적 문법**
- DB는 이를 **실행 가능한 절차(Execution Plan)** 로 변환해야 한다.

이 변환 과정에서 옵티마이저는 다음을 결정한다:

- 어떤 인덱스를 사용할지  
- 어떤 조인 순서를 적용할지  
- 어느 시점에서 필터링할지  

즉, 쿼리의 **실제 실행 경로를 자동으로 최적화**한다.

그래서 “효과적인 쿼리 저장” = **실행 계획 재사용**이며  
PreparedStatement가 중요한 이유도 여기에 있다.

---

## 4. Statement vs PreparedStatement & 쿼리 재사용

### Statement
- 실행 시마다 **쿼리를 다시 파싱·최적화**해야 함  
- 문자열 결합 구조 → **SQL Injection 취약**

### PreparedStatement
- 쿼리 구조를 먼저 **컴파일 + 실행 계획 캐싱**
- 값은 **파라미터 바인딩**으로 전달됨  
  → SQL Injection **원천 차단**
- 실행 계획 재사용 → **불필요한 비용 제거**

**즉, “효과적인 쿼리 저장” =  
쿼리 구조와 실행 계획을 재사용해 최적화하는 방식이다.**

---

## 5. 인덱스를 막 발라버리면 어떻게 되나?

인덱스는 조회 성능을 올리는 대신 **쓰기 성능을 감소**시킨다.

### 이유
INSERT / UPDATE / DELETE 발생 시  
→ **데이터 + 인덱스도 동시에 갱신**해야 함

### 따라서
모든 컬럼에 인덱스를 바르는 행위는:

- 읽기만 보면 좋아 보이지만  
- 실제로는:

  → **쓰기 병목 발생**  
  → **스토리지 낭비**  
  → **전체 시스템 성능 저하**

### 결론
**“읽기 패턴이 명확한 컬럼에, 필요한 최소한의 인덱스만 전략적으로 사용해야 한다.”**

---

## 6. 전체 스토리 한 줄 요약

- 인덱스는 RDB에서 **색인(B-Tree 기반 Key–Value 구조)** 로 동작한다.  
- `CREATE INDEX` 시 시스템 카탈로그(메타데이터)에 등록된다.  
- 옵티마이저는 이 정보를 기반으로 **최적 실행 계획을 선택**한다.  
- SQL은 선언적 문법이지만 DB는 이를 **절차적 실행 계획**으로 변환해 실행한다.  
- PreparedStatement는 **실행 계획 재사용 + Injection 방지**에 효과적이다.  
- 인덱스는 **읽기 성능 ↔ 쓰기 비용** 구조이므로 전략적 사용이 핵심이다.
